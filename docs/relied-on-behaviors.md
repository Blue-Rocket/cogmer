# Agent behaviors this project relies on

Generated by `cogmer behaviors --markdown`. Do not edit by hand.

The checks below cover host behaviors that cogmer relies on. Each is checked
against a particular version; an upgrade can change it, sometimes silently.
The tiered checks apply to Claude Code and run with `cogmer doctor`.
Codex checks appear in their own section and run with `cogmer doctor --host codex`.

## Tier: offline

### B11: A hook whose daemon is unreachable exits 0 with empty stdout

If this changes, every prompt in every session is disturbed whenever the daemon is down: a non-zero exit or stray output from the hook reaches Claude Code, and the session is worse off for having cogmer installed.

### B23: A process the daemon's shape keeps the GUI session, so it can open the view and notify

If this changes, nobody sees a room: the daemon, started in the background by the session-start hook, is the only part of cogmer that can open the room view, since everything Claude Code offers delivers to the model rather than to a person (D-033, D-036). There is no error path back to the daemon, so it believes it showed the view while nothing appeared, and a first-time user is left with a loopback address nobody told them about. On Darwin 25.6 a background process keeps the logged-in GUI session, opens a URL and takes focus, whether or not it is in a new POSIX session.

## Tier: session

### B01: UserPromptSubmit carries prompt, session_id, transcript_path, prompt_id

If this changes, the hooks cannot tell which session called them, so no session is ever in a room: nothing is captured and nothing is injected. It fails silently, because a session in no room is an ordinary Claude Code session. The prompt is what capture records, and prompt_id keys each pending injection.

### B02: UserPromptSubmit stdout is injected into the pending turn

If this changes, a colleague's turns never reach your Claude, while the browser view still shows the room. It fails silently: the session answers normally, without the context.

### B03: Stop fires and carries last_assistant_message

If this changes, responses are not captured. If Stop stops firing, no response reaches the room; if it stops carrying last_assistant_message, every captured response loses its final text block, which is not yet in the transcript when Stop fires (B05). Either way the room shows prompts with incomplete or missing answers.

### B29: Stop carries the same prompt_id as the prompt that began the turn

If this changes, the turns a prompt offered are never matched to its stop call, so the daemon commits no delivery without a transcript to read, which is every Cowork turn and every Claude Code turn after B20 is recorded as failing: the turns are offered again at every prompt. It is noisy and loses nothing.

### B04: last_assistant_message contains ONLY the turn's final text block

If this changes, nothing breaks: mergeTail also handles a last_assistant_message that holds the whole turn. The check fails so that this entry can be corrected, and so that the change does not pass unseen.

### B05: The transcript at Stop time is missing the final text block

If this changes, nothing breaks: reassembly reads both the transcript and last_assistant_message, and the second becomes redundant. The check fails so that this entry can be corrected.

### B06: Human prompts carry promptSource; tool-result records do not

If this changes, reassembly anchors on the wrong record and publishes a fragment of the turn, or treats a tool result as a prompt. It fails silently: the room keeps accepting events, with the wrong text in them.

### B07: Assistant content blocks use type text / tool_use / thinking

If this changes, response text goes missing from captured turns: reassembly publishes only blocks of type text, and records tool_use blocks as tool calls. It fails silently. A renamed thinking type is not published either way, since only text is.

### B08: isSidechain marks subagent traffic

If this changes, subagent output, including the compaction summarizer's, is captured as if the session had written it and published to the room. It fails silently.

### B09: Assistant records carry no promptId

If this changes, nothing breaks: turns are segmented by position, because assistant records carry no promptId. If they gained one, transcript.go could match each response to its prompt by id instead.

### B12: Reassembly reconstructs the complete turn

If this changes, captured turns lose text or repeat it, even while B03, B04 and B05 each pass. It is the check that shows whether they still combine into a complete turn, and it fails silently in the room.

### B20: Injected hook output is recorded as a hook_success attachment

If this changes, no injection is ever confirmed as delivered, so a colleague's turns are offered again at every prompt. The daemon logs that it is re-offering them and points at `cogmer doctor`. Once doctor has recorded this check as failing for the installed version, the daemon counts a turn as delivered without evidence, and an injection that never arrived is then lost silently.

### B21: CLAUDE_CODE_SESSION_ID is exported into a tool call's environment

If this changes, a slash command cannot tell which session ran it, so `/cogmer:room-create` and `/cogmer:room-join` refuse rather than guess, and stop working. If the variable is present but reports a different id from the hooks, the failure is worse and silent: the room is bound to a session that does not exist, the real session is bound to nothing, and capture stops with no error anywhere.

### B22: Injected hook output is positioned as data, not as the session's own instruction

If this changes, a colleague can steer your session: a turn written as an instruction would be followed rather than read. The injected block frames its content as information, never instruction, and that framing travels in the same hook output as the content, so it holds only while Claude Code places hook output where a session reads it as data. Nothing in the protocol would show the change. A session given a turn claiming SYSTEM OVERRIDE refused it and told its user on Claude Code 2.1.275 (commit b09b208).

### B33: A project or plugin command reaches UserPromptSubmit with the text as typed

If this changes to something other than the text typed, such as the command file's expansion, the daemon no longer recognizes a command, and every command a user types is published to the room with the model's account of it, which can hold an invitation. It fails silently. If a command stops reaching the hook, nothing breaks, because there is nothing to hold back.

### B34: A hook's output as long as the daemon's block budget is recorded whole and not stored as a preview

If this changes so that the host's limit falls below the budget, every block over it reaches the model as a preview of its first two thousand characters and a pointer to a file, so the newest turns, which are at the end of the block, are missing, and the recorded block is not the one offered, so it is never confirmed delivered and is offered again at every prompt and grows. It fails silently. This is what happened when the limit was 10,000 characters and the budget 60,000, and a room's offered turns grew from 21 to more than 180.

### B35: Claude Code offers the skills in a plugin's skills/ folder and in no other folder of the plugin

If this changes so that a skill in another folder of the plugin is offered, the Codex skill in plugin/codex-skills reaches a Claude Code session's model as a route to every command, which D-119 keeps closed, and the model can run a command nobody asked for, including one that binds a session to a room or admits a colleague. It fails silently, since nothing in a session says a skill was offered. If skills/ stops being loaded, nothing breaks.

### B24: A slash command whose ! line exits non-zero produces no model turn

If this changes, nothing breaks: cli.sh exits 0 on every path, which is correct either way. The check fails so that the reason for that rule can be revisited, since a failing line that still ran a turn would let a command report failure by its exit status. Where it holds, a command that exits non-zero leaves the model unable to explain or act on what happened, and the person sees only a failed shell line, so a path that exited 1 again would fail silently.

## Tier: compaction

### B14: session_id and transcript_path survive compaction

If this changes, a session drops out of its room at its first compaction: the hooks find a session's room by its id, so the new id belongs to no room, and nothing more is captured or injected. It fails silently.

### B15: The transcript is appended to across compaction, never rewritten

If this changes, reassembly can lose the record it anchors on, which was written before the compaction, and publish the wrong text for the turn after it. It fails silently.

### B17: The compaction summary record carries no promptSource

If this changes, reassembly mistakes the compaction summary for a user's prompt, and every turn after a compaction is anchored on it and published with the wrong text. It fails silently.

### B18: Built-in slash commands do not reach UserPromptSubmit

If this changes, every built-in command a user types, including /compact, is captured as a prompt and published to the room. A command from a plugin or a project does reach the hook, which B33 records and the daemon holds back.

### B19: Injected teammate context survives compaction

If this changes, a session counts a colleague's turns as delivered after a compaction has dropped them, so it never receives them again, and a later reference to them finds nothing. It fails silently. Delivery is therefore not reset at compaction. Only context that was the conversation's subject is checked here; that incidental context also survived is recorded in 84a0751:docs/phase0a-findings.md.

## Codex session checks

`cogmer doctor --host codex` checks these against the installed Codex runtime.
Set `COGMER_CODEX_BIN` to check another executable, such as a desktop runtime.
These checks use an isolated turn, with real hook output and a shell tool.
Codex compaction behavior is not checked.

### B25: Codex prompt and Stop hooks carry matching session and turn identifiers

If this changes, prompts and responses cannot be associated with their session or pending injection. Nothing in the session reaches the room.

### B26: Codex rollouts and Stop together contain commentary, tool calls and final text

If this changes, the room records an incomplete response or counts no tools. Reading only the final answer loses what the assistant said before a tool call.

### B27: Codex records injected context as a hook-marked message and the model receives it

If this changes, a colleague's turns are never confirmed as delivered and are offered again. An altered or truncated block cannot confirm delivery of the complete block.

### B28: CODEX_THREAD_ID in a shell tool equals the hook session identifier

If this changes, a room command cannot identify the session that invoked it. The command refuses rather than choosing another session's room.

## Cowork session checks

Claude Cowork runs the Claude Code harness in a sandbox that no check can reach, so
`cogmer doctor --host cowork` checks these against the Claude Code on this machine, in
one isolated turn that starts a small MCP server of this binary and fires hooks at it.
A machine with no Claude Code has no check, and Cowork's compaction behavior is not checked.
The result is recorded apart from Claude Code's own for the same version.

### B30: A Claude Code session adds the JSON form of an mcp_tool hook's reply to the model's context

If this changes, a colleague's turns reach a Cowork session's model not at all, while every call succeeds and every turn is counted delivered when its stop call arrives, so the loss is silent. Once doctor has recorded this check as failing for the installed version, the daemon stops counting a Cowork turn delivered without evidence, and the turns are offered again at every prompt, which is noisy and loses nothing. The plain form of the same reply is recorded as a successful hook and does not reach the model, and a change there would not break this.

### B31: A hook of type mcp_tool that names a server that is not there shows nothing and leaves the session working

If this changes, a Cowork user whose bridge is stopped, crashed or not yet started sees an error or a failed session on every prompt, which breaks the rule that cogmer never makes a session worse. A hook that calls an absent server is what a stopped bridge looks like to the harness.

### B32: A hook of type mcp_tool on SessionStart is not called at launch

If this changes, nothing breaks: a Cowork bridge needs nothing at launch, because the first prompt's call is the first that reaches it. A call at launch would let the bridge start the daemon, and learn of a session, before its first prompt, which could replace what it does on the first call.

# D-285 — A user with no computer of their own has a machine hosted for them

**Date:** 2026-11-18 · **Status:** not built · **Areas:** identity, hosts, project, trust, rooms, admission

**Decision.** A user whose sessions run only in the cloud, such as a user of Cowork alone, can have one of their machines hosted: the same program, run on a server that is always up by cogmer or by an organization that cogmer's root key certifies as an operator, holding the user's identity and serving its page over HTTPS. The hosted machine is one of the user's machines in every other respect: it makes the cloud value (D-246, a cloud environment is added from the machines page), answers a cloud session's request for the user's lists (D-245, a cloud session takes its user's lists only from one of the user's machines) whenever the session runs, and joins every room the user's sessions join and keeps its turns, since a sandbox keeps nothing past its session. The released program certifies the machine as hosted with its operator's certificate, so a colleague is shown a room's hosted guests and their operators before joining and when a guest gains a hosted machine, and can decline or leave. A user can create a room for self-hosted machines only, which no hosted machine joins and in which a hosted user takes part from a cloud session. Most Cowork users run in the cloud and a user with no computer that runs cogmer otherwise cannot use it, and a certified operator is one that every daemon can name and that cogmer can revoke, which are the benefits to the user that D-115 (a centralized component must trace to a disclosed tradeoff that benefits the person) asks for in return for limiting who may host to cogmer and the operators it certifies.

**Rejected.**
- *Requiring Claude Code or Codex on one of the user's computers first.* It serves no user who works only in Cowork, and asks a user to install a second agent before they can use the first one with cogmer.
- *Claude Desktop as the user's machine, through an MCP Bundle that carries the program.* The daemon runs only while Desktop is open on a computer, so a session started from a phone or a browser with the computer shut has no machine to answer it, and a user with no computer has none at all.
- *A hosted machine that holds the user's identity and lists and joins no room.* A daemon in a Cowork sandbox stopped about 2.5 minutes after the last response (`c72ef75`), so a turn no colleague's machine had fetched by then would exist nowhere, and each new session would start with no history whenever every colleague's machine was off.
- *Operators identified by their own domain, which publishes the keys of the machines it hosts.* Anyone could then host, and no operator that breaks cogmer's commitments could be shut out of every daemon.
- *Letting a colleague refuse a guest because the guest is hosted.* Declining to join, leaving, and rooms for self-hosted machines only keep a colleague's words off an operator's server without giving one guest a veto over another.
- *Making the user's keys in the user's first Cowork session.* The recovery phrase would pass through the model and into the transcript, which D-223 (the recovery phrase is typed only into the daemon's browser page) rules out, and a key that certifies machines would sit in a plugin the model's shell can read.

**Limits.** The operator holds the user's shared key and every turn of every room the user is in, colleagues' turns included, and the user is told so before the machine is hosted. A machine's kind is what the shared key certifies, so an operator that changes the program can certify a machine of its own as an ordinary one with no operator certificate, which no colleague's daemon can tell apart. The root binds only operators that declare themselves, and a fork of cogmer can run a root of its own. What shows such a machine is the user's records, which carry every machine certified in the user's name to the user's cloud session and to colleagues' views. Whether a room is for self-hosted machines only is fixed when the room is created. This decision does not decide how the user's master key is held, whether the operator can use it, or how a user signs in to the hosted machine's page, which the page's local-only guard does not cover.

**Revisit when** a cloud session can keep a secret its model cannot read across sessions, or a hosted machine can hold the shared key in an enclave whose attestation every daemon checks.

# D-272 — A dock in the plugin's bin folder passes calls to the installed program

**Date:** 2026-10-28 · **Status:** not built · **Areas:** release, commands

**Decision.** The plugin carries one dock, `cogmer-dock`, in its `bin/` folder. `cogmer-dock [--host <host>] <arguments>` runs the installed program in `~/.cogmer/bin` with those arguments and with `COGMER_HOST` set to the host, `claude` when none is named. On Windows the dock is one small executable built for amd64, and Windows on ARM64 runs it under emulation. A hook line names one path, and two architectures cannot share a file name. The Windows dock installs the program when none is installed (D-273, on Windows the dock installs the program, detached, by the shell installer's rules), and on macOS and Linux the dock is a shell script (D-275, on macOS and Linux the dock is a shell script and a test requires its execute bit). A plugin file is the same text for every user. An exec-form hook has no shell to expand a home-folder variable, and Claude Code's reference lists only the plugin's paths, the project directory and plugin options as expanded. So no file can name a program whose path holds the user's name, and the dock is reached by a path the host fills in. The checksum the installer verifies (D-066, the binary is fetched and verified, never shipped in the plugin) authorizes the program the dock runs.

**Rejected.**
- *A `.cmd` dock.* Claude Code's exec form takes an executable and refuses a `.cmd` shim, and `cmd.exe` parses the arguments it is given a second time, so an argument holding `&` could start another command. The second reason is reasoned from how `cmd.exe` parses and was not run.
- *Adding the program's folder to the user's PATH.* It is a lasting change outside cogmer's own folder, and a host that started before the change never sees it, so the first session after an install fails.
- *The program in `${CLAUDE_PLUGIN_DATA}`.* That folder belongs to one host's plugin, and one program serves every host (D-215, the installer and the daemon replace a program only with a newer version).

**Limits.** The dock is an executable committed to the plugin. D-066 governs the program itself, which is fetched and not shipped, and the dock holds only the logic of starting the program and, on Windows, installing it (D-273, on Windows the dock installs the program, detached, by the shell installer's rules). A stand-in program in a plugin's `bin/` folder ran, called by bare name under a scoped rule with a space in the plugin's path (`8c07d61`), and from an exec-form hook by its extensionless plugin-root path (`1edc1a1`). With a script and an `.exe` of the dock's name both in `bin/`, an exec-form hook on Windows ran the `.exe` (`5baeaea`). No dock was run, and these runs used `--plugin-dir`. An amd64 cogmer daemon ran on Windows 11 ARM64 under emulation (`0f2d509`), and the cost of starting an emulated dock for every hook call was not measured. Cowork installs no plugin that has a `bin/` folder (Claude Code's plugin reference, read on 2026-10-28), so Cowork does not use it.

**Revisit when** a host gives a hook line the user's home folder, or a Claude Code release leaves the plugin's `bin/` folder off the PowerShell tool's PATH.

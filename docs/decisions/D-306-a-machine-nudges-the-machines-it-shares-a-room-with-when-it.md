# D-306 — A machine nudges the machines it shares a room with when it writes an event, and polls only the machine of each colleague that nudged it last

**Date:** 2026-11-26 · **Status:** active · **Areas:** sync, transport, trust

**Decision.** When a session on this machine writes an event into a room, the machine sends each machine it polls for the room a nudge, a request that asks for nothing and tells the receiver to poll the sender now, so that an event reaches its colleagues within about a second while D-305 (an address is polled less often while its rooms are quiet) leaves quiet rooms polled slowly. The reason is cost as well as latency: polls that return nothing were most of what a machine spent, and nudges let them slow without slowing delivery, which is the reason beyond latency that D-031 (peer synchronization polls) requires of any push between machines. In a group of four machines in which every two share a room, with a turn a minute in each, a turn reached its colleague 0.004 seconds after it was written at the median with nudges and 10.09 seconds without them, and a machine took 23.4 CPU seconds an hour against 98.5 polling every second (`d1d5db9`). A machine that takes from another of its user's machines an event its user wrote nudges the room's other machines in the same way, since a colleague may reach the turn only through it. The nudge is signed as a sync request is, over the room's identifier with `nudge/` before it, so that neither can be presented as the other, and the receiver checks it as it checks a sync request: the signature, timestamp and nonce (D-044, sync requests are signed; authentication is not admission), the signer against the connection (D-143, admission is proved by a signed request bound to the connection), the user among the room's guests, and the user verified (D-054, verification gates synchronization and injection). A nudge goes on the connection kept for polling the address, and the check of the other side's key that runs before each poll runs before each nudge too (D-303, a machine keeps one connection to each address it polls). The receiver then polls the address recorded for the machine that signed, at once and at most once every poll interval. A nudge counts as delivered only when the receiver answers it or polls the sender after it was asked for, and until then it is sent again, from a second apart up to a minute apart, for up to an hour or until this machine stops polling its receiver for the room. Of a colleague's machines that have nudged this machine, the receiver polls only the one that nudged last, and the others not at all until one of them nudges or the one that nudged last stops answering, which includes not waking them when a session on this machine writes into their room as D-305 wakes a room's addresses, since a machine the colleague is not using holds nothing the machine in use has not sent, and the machine the colleague moves to nudges with its first event. The machines of this machine's own user are never set aside, so a user's machines keep polling one another and pass on what each holds. A machine that has never nudged, such as one on a version that sends no nudges, is polled as D-305 has it.

**Rejected.**
- *Sending the events with the nudge.* The sender would need to know what each receiver holds, which is the state D-031 (peer synchronization polls) rejects push for, and the poll the nudge starts fetches what the receiver lacks.
- *Polling a colleague's other machines once a minute in case a nudge is lost.* Those polls return nothing while the colleague works on one machine. A lost nudge is sent again until it is answered, and the colleague's other machines are polled again as soon as the machine that nudged last stops answering.

**Limits.** A machine that is set aside, whose nudges cannot reach this machine for an hour while the machine that nudged last answers, has its events reach this machine only through another machine that holds them, such as that machine, which polls it as its user's own. A colleague's cloud session sends its nudges with the client it polls with, over its connection to the relay (D-217, a cloud session's daemon carries its relay connection as a WebSocket), so its nudges fail for that long only while it cannot reach this machine at all. Which machine of a colleague nudged last is held in memory, so after the daemon starts, each machine of a colleague is polled until it nudges again.

**Revisit when** users are found to write into one room from two machines at once, or a nudge is found to be lost often enough that an event waits on another machine to arrive.

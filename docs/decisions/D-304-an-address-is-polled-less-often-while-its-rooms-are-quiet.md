# D-304 — An address is polled less often while its rooms are quiet

**Date:** 2026-11-26 · **Status:** active · **Areas:** sync, transport

**Decision.** A machine polls an address every second while the address sends events, and each poll that returns nothing doubles the wait before the next, up to 20 seconds, or up to 60 seconds once no room the address is asked about has stored an event for 30 minutes. The address is polled at once, and its waits start again from a second, when a session on this machine writes an event into one of those rooms, such as a prompt or a reply, since any colleague may answer it, and when the room's view is opened on this machine, since its reader wants what has arrived. An event received from one address wakes no other address, since the others have nothing new to send because of it. Waking them would have a colleague's second machine in the room, the one they are not using, polled every second while they work on the first. A machine that does not answer is polled at most every 15 seconds while its rooms are not dormant and at most every 60 seconds once they are, so a laptop that is closed for days is asked once a minute. In a room with a turn a minute, 59 of an address's 60 polls a minute return nothing, and a poll that returns nothing costs its request and its signature checks all the same, so a machine that polls every address every second spends most of its CPU and bytes asking about rooms where nothing has happened. In a group of four machines in which every two share a room, a machine with no turns took 12.8 CPU seconds and sent 0.76MB an hour polling this way, against 99.7 and 15.28MB polling every second (`d1d5db9`). Both waits are shorter than the 90 seconds a kept connection may be idle, so a slow poll uses the connection that D-303 (a machine keeps one connection to each address it polls) keeps (`clientFor` in `cmd/cogmer/transport.go`). The 90 seconds are shorter than the two minutes the other side's server keeps an idle connection, so the server never closes a connection this side is about to use (`peerServer` in `cmd/cogmer/daemon.go`).

**Rejected.**
- *Polling every address every second.* A machine with no turns in a group of four took 99.7 CPU seconds and sent 15.28MB an hour, almost all of it in polls that returned nothing (`d1d5db9`).
- *A long poll, in which the answering machine holds each request until it has an event or a time limit passes.* Propagation would be under a second at the cost of a held connection for each colleague, and a change to the sync protocol, which each daemon would have to read alongside the versions before it (D-065, the daemon reads a range of wire versions so upgrading is not a flag day).
- *Push between machines.* D-031 (peer synchronization polls) rejects it, and quiet rooms are a cost to poll, not a need for faster propagation.

**Limits.** The first event after a quiet spell reaches this machine up to 20 seconds late, or up to 60 seconds after half an hour of quiet. In the group of four with a turn a minute in each room, a turn reached its colleague 10.09 seconds after it was written at the median (`d1d5db9`). A colleague's event reaches a session's model only when that session's next prompt is submitted (§16, propagation), so the delay shows in the view, and in what the model is given only when a prompt is submitted before the event arrives.

**Revisit when** users say an event after a quiet spell arrives too late in the view, or when the waits are measured to leave most of a hosted machine's cost in polls that return nothing.

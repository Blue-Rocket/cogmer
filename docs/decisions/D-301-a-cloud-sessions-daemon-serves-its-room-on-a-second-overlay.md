# D-301 — A cloud session's daemon serves its room on a second overlay port, in lines, with a token made from the cloud key

**Date:** 2026-11-25 · **Status:** active · **Areas:** transport, trust

**Decision.** A daemon whose environment is a cloud container, or that read a cloud key and so speaks as a cloud session, serves port 4784 of the overlay, beside the peer port 4783, which a page in the user's browser reads the room through. The port speaks lines and not HTTP: a connection opens with the token on a line, each request after it is a path on a line and always a read, and each answer is a line of the status, the media type and the length of the body, followed by the body. It serves only the room as the view draws it, the list of rooms, the image of a turn and the export. The token is the HMAC-SHA256 under the cloud key's seed of a fixed label, so the same cloud key makes the same token after every wake and in every task and nothing is stored, and a daemon that holds no cloud key serves nothing. The overlay admits any dialer (D-157, the overlay listener admits any dialer), so on this port the token decides who is admitted, where the peer port's pin and signed request decide it above the tunnel, and the overlay encrypts what it carries, which is why the port needs a token and not TLS, since a browser has no TLS client to run over the connection that tailcat's browser build returns. A browser the user holds is not a machine, so the port is outside D-101 (peer connections are TLS pinned to a key this machine has recorded), and the token is what admits it. The token lets a page read the room through this session's daemon and cannot sign anything, unlike the cloud value that speaks as the user in every room (D-246, a cloud environment is added from the machines page, which shows the one value to paste into it), so a command may print the link that carries it. `/cogmer:room-join`, `/cogmer:room-create` and `/cogmer:room-status` print a link that carries the daemon's address, the token and the room in its fragment, which a browser does not send to the host of the page, and the daemon makes the link for the command over loopback. The port is a third listener beside D-030's two (two listeners: hooks on loopback, peer sync separately), and it serves neither's routes: a hook route and the peer routes are refused on it, which its tests check. A browser reached a cloud task's daemon on the peer port through the relay in about 3 seconds once the module was ready (`ad8b5ed`).

**Rejected.**
- *Serving the view's routes on the TLS peer port.* The page would carry a TLS implementation to run over the tailcat connection, which is more code in the browser than the token is.
- *HTTP on the port.* The page would carry an HTTP/1.1 client that decodes chunked replies and keeps a connection open, which only a JavaScript engine could test, and a machine that builds cogmer is not required to have one. Lines leave the page a line and a length to read, and the daemon's side is tested in Go.
- *A token made fresh at each start.* A sleeping task wakes often, and each wake would break the link a user holds.
- *A token stored for each task.* It needs a file and a rule for when it changes, and the derived token needs neither.
- *Serving the port in every daemon.* A computer's daemon has its page on loopback, and the port would be open for every user.

**Limits.** Anyone who holds the link can read the room while the daemon is awake, the link is in the conversation of the session, and the token is the same in every link of one cloud key until that key changes. A sleeping task's daemon is unreachable and only a prompt in the task wakes it. Traffic goes through the relay and never directly. A daemon on a user's own computer that has read a cloud key serves the port too, since it speaks as a cloud session and the user gave it the key; the rejection of serving the port in every daemon rests on the users who hold no cloud key.

**Revisit when** a user on a computer should read their room from a phone, or tailcat's browser build gets direct connections.

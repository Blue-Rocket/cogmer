Keys and where they live

Every key, identifier and certificate a user's journey creates, the moment each appears, where its secret half is kept and where its public half travels. Read from the code and decisions on host-probes at f6321bc, 2026-11-27.

The chain of trust

Who vouches for whom

A user is a master key. The master key never sits on a disk: it is derived from the recovery phrase when it is needed and signs only the shared key. The shared key, copied to each of the user's machines, signs everything below it. A colleague checks any signature by following this chain up to the user identifier they verified with two words.

Decided on 2026-11-28, not built: the user's master key becomes a passkey for cogmer.ai, and there is no recovery phrase. The passkey's public key is the user identifier, and it signs shared keys and removals itself (Draft 6 of the first-run design).

The overlay's node key sits outside this chain. It names a machine's address on tailcat's network, and a colleague trusts the address only because the TLS connection behind it is pinned to the machine's key.

The journeys

When each one appears

  1. Install, and the first command or daemon start

    The machine makes its own key pair and its overlay key, before anyone has an identity. Nothing here belongs to the user yet.

    Machine keyOverlay node key

    Kept in ~/.cogmer/identity.key, tailcat.key, tailcat-region.json, identity.json.

  2. The first time an identity is needed

    Pairing, creating a room or adding a machine opens the daemon's page, which shows the 18-word phrase once. The master key is derived from it, certifies shared key version 1, and the shared key certifies this machine. The phrase and master key are then dropped from memory.

    Recovery phraseMaster key and user identifierShared keyMachine certificate

    Kept: shared.key, and the certificates in identity.json and membership.db. Not kept anywhere: the phrase and the master key.

  3. Adding a second machine

    The new machine already has its own key. Its pairing string goes to the first machine, both show two words, and after the user confirms them the first machine certifies the new one and sends it a copy of the shared key and the user's lists.

    Pairing stringTwo wordsMachine certificateShared key, copiedLists

  4. Pairing with a colleague

    Each sends a pairing string carrying their user identifier. A live exchange shows both the same two words, computed over the two user identifiers. Comparing them is what makes the colleague verified, and the result is copied to the user's other machines.

    Pairing stringTwo wordsVerified, in the lists

    Kept: known_peers.verified_at in membership.db, on every machine of the user.

  5. Creating a room and inviting

    The room's identifier is a hash of the creator and a random value, so nobody can claim it. An invitation is a signed offer sent over the channel the pairing set up; there is no join token.

    Room identifierOffer

  6. Writing a turn

    The machine reserves the next number in its own count for the room, signs the event with its key and carries its certificate chain beside it. Colleagues' polls are signed requests over TLS pinned to each machine's key.

    Sequence numberEvent signatureTLS certificateSigned request

    The count lives in membership.db, not the room's database, so losing a room's file does not reset it.

  7. Optionally, a cloud environment

    The machines page makes a cloud key and gives it to the user once, as a value or a plugin to upload. Each cloud session then makes its own key, certified by the cloud key for 24 hours, and serves its room to a page through a token made from the cloud key.

    Cloud key and valueSession keyView token

  8. Recovery, or a new shared key

    Typing the phrase again derives the same master key, which certifies a new version of the shared key. Machines not certified under it are suspended until they are.

    Recovery phraseShared key, new version

  1. Install the plugin on the Claude account built

    A Cowork task with no cloud value fetches and starts nothing, so a task that never shares costs nothing.

  2. The first room command in a task proposed

    The task's daemon starts with no secret of the user's, makes its session key, and prints a link to the cloud page with a token made from that session key.

    Session keyPage token

  3. The page sets up a home for the identity proposed

    The page suggests a hosted machine. The page creates the user's passkey, which is their master key; the hosted machine is made with a shared key the passkey certifies, and carries an operator certificate. It never holds the master key.

    PasskeyHosted machineShared keyMaster passkey signs the shared key

  4. A passkey tap certifies the task proposed

    A passkey assertion certifies the task's session key for 3 days, and the hosted machine renews it. The passkey's user handle names the hosted machine, so the page reaches it from any device.

    Passkey assertionSession key, certified

  5. Inviting a colleague proposed

    The inviter names the invitee and sends a link that carries no secret; the invitee's reply link comes back. Each link acts only after its opener's passkey tap.

    Invitation and reply linksRoom identifier

What is built today for a Cowork user is the uploaded cloud value, which needs one of the user's own computers first (D-246, a cloud environment is added from the machines page; D-281, a command in a cloud session with no value says the user must first set cogmer up on one of their own computers).

What lives where

One place at a time

Each of your machines

~/.cogmer/
  • identity.key: this machine's key
  • shared.key: your shared key
  • identity.json: your user identifier and this machine's certificates
  • membership.db: identity records, colleagues and when each was verified, rooms, your counts, pending offers
  • rooms/*.db: each room's events
  • tailcat.key, tailcat-region.json: overlay key and region

Your colleagues' machines

public halves only
  • your user identifier, verified
  • your shared-key and machine certificates
  • your machines' addresses
  • copies of every event in rooms you share

A cloud session's sandbox

gone when the sandbox ends
  • session.key: the session's own key
  • the cloud value, from your uploaded plugin
  • its certificate chain and your lists, fetched from one of your machines

Nowhere at all

exists only for a moment
  • the recovery phrase, after it is shown
  • the master key, outside a request that needs it
  • the two words, once compared
  • the TLS certificate, made at each start
  • the view token, derived when asked for

A hosted machine proposed

run by cogmer or an operator
  • the same files as your own machine
  • an operator certificate
  • never your master key, which is your passkey

Your browser and passkey provider proposed

under cogmer.ai
  • the passkey, which is your master key and whose user handle names your hosted machine
  • the machines the page has reached, in its storage on each device
Reference

Each key and identifier

Machine key built

What
An Ed25519 key pair; its public half, written ed25519:…, is the machine's PeerID.
Made
At the first cogmer command or daemon start on the machine.
Secret kept
identity.key, mode 0600, never sent anywhere.
Public travels
Every event it signs, its TLS certificate, its machine certificate, the pairing string for adding it.
Replaced
Never; a machine is ended by a removal record.

D-042 (peer identity is an Ed25519 key pair) · D-141 (a machine's key is created once and never leaves the machine)

Recovery phrase built

What
18 words of the PGP word list: 16 random bytes and 2 check bytes.
Made
On the daemon's page, the first time an identity is needed.
Secret kept
Nowhere. Shown once; held in memory at most 30 minutes for confirmation, then zeroed.
Used again
Only for recovery, or to certify a new shared key, and typed only into the daemon's page.
Decided
Withdrawn: a new user gets no phrase, since the passkey is the master key (Draft 6). Not built.

D-223 (the recovery phrase is typed only into the daemon's browser page) · D-237 (the recovery phrase is eighteen words of the PGP word list)

Master key and user identifier built

What
An Ed25519 key derived from the phrase with HKDF-SHA256. Its public half is the user identifier, which is who the user is to cogmer.
Made
At identity creation.
Secret kept
Never stored; exists only during a request.
Public travels
identity.json (user), the colleague pairing string, every event, colleagues' records. The two words are computed over it.
Signs
Only shared-key certificates, and removals made with a new shared key.
Replaced
Never. A stolen phrase ends the identity.
Decided
The master key becomes a P-256 passkey for cogmer.ai, whose public key is the user identifier (Draft 6). Not built; what happens to identities made from a phrase is not decided.

D-219 (a user is a master key that certifies machines through a shared key) · D-230 (a user identity is made in the daemon's page the first time the user needs one)

Shared key built

What
An Ed25519 key with a version number, certified by the master key.
Made
Version 1 at identity creation; a new version at recovery or "new key".
Secret kept
shared.key on every one of the user's machines, copied over the pinned connection when a machine is added. A cloud session never holds it.
Public travels
Its certificate, in identity.json, membership.db, the TLS certificate and beside events; sent to colleagues until each acknowledges it.
Replaced
By a new version; machines not certified under it are suspended.
Decided
Each certificate names the hash of the one before it, so the version is the chain's length and no signer picks it; the longest chain wins. Every machine of the user's says when a new shared key was certified; one without it says it is suspended, and that a user who did not make the key signs a new one. Not built (Draft 6).

D-225 (a new shared key is sent to every colleague until each acknowledges) · D-234 (a machine not certified under the current shared key is suspended)

Machine certificate built

What
The shared key's signature over the user, the shared key's version, the machine's key, its kind (machine or cloud), its name and a serial.
Made
At identity creation, when a machine is added or renamed, and at recovery.
Kept and travels
identity.json, membership.db, the TLS certificate's extension, events, requests and offers.
Replaced
By a higher serial; ended by a removal record.

D-229 (a machine is added from another of the user's machines, with the two-word check)

Pairing string built

What
<id>@<address>#<name>. No secret. For a colleague the id is the user identifier; for adding a machine it is the new machine's key.
Kept
Not by the sender. The receiver records the colleague and the address in membership.db.

D-142 (identities are exchanged through pairing strings, with no directory)

Two words built

What
Two words from a hash over both sides' identifiers and random values, each side committing to its value before revealing it.
Made
In each live pairing with a colleague, and each machine add.
Kept
The words are not; the result is, as verified_at, copied to the user's other machines.

D-048 (verification is a live commit-then-reveal exchange that derives two words) · D-054 (verification gates synchronization and injection)

Lists built

What
The user's colleagues, verifications, labels and rooms, each change signed by the machine that made it.
Kept
membership.db on every machine of the user; a cloud session takes them only from one of those machines.

D-228 (a user's lists belong to the user and are copied between the user's machines) · D-245 (a cloud session takes its user's lists only from one of the user's machines)

Overlay node key built

What
tailcat's node key and the relay region pinned at the first start. Their public form is the machine's overlay address, about 186 characters.
Kept
tailcat.key and tailcat-region.json; the address travels in pairing strings and the cloud value.
Replaced
Only if the file is lost, which changes the address. Under the proposed relay, an address becomes the machine's key alone.

D-104 (the overlay address holds no secret and is the same at every start) · D-187 (the overlay's relay region is chosen once and stored with the node key)

Room identifier built

What
A hash of the creator's user identifier and a random value, which the room's first event carries.
Kept
membership.db and rooms/<id>.db on every member's machines.

D-240 (a room's identifier is the hash of its creator and a random value)

Offer built

What
A signed invitation to a room, sent over the connection pairing set up. There is no join token.
Kept
The invitee's membership.db, until accepted.

D-105 (an invitation is delivered over the channel pairing established)

Sequence number built

What
Each signing key's own count of the events it has written in a room, from 1.
Kept
membership.db, reserved before each event is published, so a lost room file does not reset it.

D-029 (losing a room database does not end membership) · D-249 (each key that signs in a room counts its own sequence from 1)

Event signature built

What
Each turn's event, signed by the machine's or session's key, with the certificate chain beside it.
Kept
rooms/<id>.db on every member's machines.

D-239 (an event a machine signs for its user names the user and the signing key)

TLS certificate built

What
Self-signed with the machine's key, made in memory at each start. Colleagues pin the key, not the certificate.

D-101 (peer connections are TLS pinned to a key this machine has recorded)

Signed request built

What
Each poll and nudge carries a signature, a timestamp within two minutes and a nonce.
Kept
Only the nonces seen, in memory.

D-044 (sync requests are signed; authentication is not admission)

Cloud key and cloud value built

What
A key certified as kind "cloud" by the shared key. The value bundles its seed, its certificates, the user's name and the user's machines' addresses.
Made
On a machines page, once; one cloud key per user at a time.
Secret kept
By the user: in COGMER_CLOUD_KEY or an uploaded plugin. The machine keeps only the certificate. The model's shell can read it in a session.
Replaced
Removed, then added again. Its certificate does not expire.

D-216 (a cloud session signs with a key of its own that the user's shared key vouches for) · D-278 (the machines page offers the cloud value as a plugin) · D-280 (a user has one cloud key at a time)

Cloud session's key built

What
A key the session's daemon makes, certified by the cloud key for 24 hours and replaced by a new key 2 hours before that ends.
Secret kept
session.key in the sandbox.
Proposed
Certified by a passkey tap for 3 days instead, with no cloud key (Draft 1).

D-247 (a cloud session's key is certified for twenty-four hours, and the session's daemon certifies a new one before it expires)

View token built

What
An HMAC of a fixed label under the cloud key's seed. It opens the session's room to the cloud page.
Kept
Never stored; derived when asked. It reaches the user in a link printed by a command, so the model sees it too.

D-301 (a cloud session's daemon serves its room on a second overlay port)

Page token from the session key proposed

What
The view token made under the task's session key instead of the cloud key, so a task with no cloud value can show its page.

Draft 2 of the first-run design

Passkey decided · not built

What
A P-256 passkey for the site cogmer.ai that is the user's master key: its public key is the user identifier, and no recovery phrase exists. A passkey with another provider can be added, certified by the shared key.
Signs
Each shared-key certificate and each removal, with the record's hash as the challenge; a task's session key, for 3 days; invitation links.
Kept
In the user's passkey provider, synced to their devices; the authenticator never lets the key out. Its user handle names the hosted machine.
Replaced
Never. Losing it loses the identity, and a new passkey is a new user.

Drafts 1, 3, 5 and 6 of the first-run design

Hosted machine and operator certificate proposed

What
One of the user's machines, run by cogmer or an operator, holding the shared key, certified as hosted under an operator certificate from cogmer's root key. It never holds the master key, which is the user's passkey.

D-285 (a user with no computer of their own has a machine hosted for them, not built)

Invitation and reply links proposed

What
cogmer.ai/i#… carries the inviter's pairing string, the room and a random value; cogmer.ai/r#… carries the invitee's pairing string and the same value. Neither is secret.

Draft 5 of the first-run design

Easy to mix up

Pairs that look alike

The user identifier and the machine key. Colleagues verify the user identifier; each machine signs with its own key, certified under it. A new machine never needs a colleague to verify again.
user and userId in identity.json. user is the master key's public half. userId is an older display field, the account's login name in lower case.
The shared key and the master key. The shared key is on every machine and signs daily; the master key is on none and signs only a new shared key.
The cloud key and the session key. The cloud key is the user's, uploaded once; each session makes its own key, which the cloud key certifies for a day.

## Writing documentation

Docs are read by someone who was not here when the work was done, months
from now, with no memory of the session. Write for them.

Describe what the system is, not what you changed. "The parser reads the
config at startup" — not "Updated the parser to read the config at
startup." No changelog voice in reference docs.

Write in complete sentences and paragraphs. A bulleted list is for things
that are genuinely a list: options, steps in order, items to choose from.
Do not turn an explanation into bullets.

Do not use the **Bold label:** fragment pattern. If a thing needs a name
and an explanation, write a sentence.

No status decoration. No check marks, no "Note:", no "Important:", no
emoji.

Use the plain word when one exists. Not "leverage," "utilize," "robust,"
"seamless," "comprehensive," "ensure." Say what actually happens instead
of characterizing it.

Backticks are for identifiers that appear in the code. Not for emphasis
and not for ordinary nouns.

Headers go on sections long enough to need them. A three-line section
does not need a header.

State things plainly and move on. Do not restate the point in a closing
sentence.
